# 0005 — 远程农场：GA 仅自托管

- 状态（Status）：accepted
- 日期（Date）：2026-10-20
- 决策者（Deciders）：项目维护者

> **English abstract**: PolyPack ships self-hosted farms only through GA and the 1.x line. The project provides software and deployment guidance, never compute: user source stays on the origin and user-owned build site, credentials are resolved only at the build site through `CredentialRef`, and the project never receives source, artifacts, logs, or keys. Multi-tenant hosting is a separate business with tenant isolation, key custody, compliance, and on-call obligations; offering it would require a superseding ADR and an explicit revision of the ROADMAP §2 non-goal. BYOC, if ever pursued, precedes multi-tenant hosting.

## 背景（Context）

农场 v1 已具备协议、worker、隔离、共享缓存与部署指南（[`docs/FARM.md`](../FARM.md)、[`docs/FARM-DEPLOY.md`](../FARM-DEPLOY.md)、`crates/polypack-cli/src/farm.rs`）。它解决的是 Apple 系目标必须 macOS 宿主、Windows / Linux 用户需要一台构建机的问题。当前模型是「发起地决定构建什么，构建地决定怎么构建并独占凭据」，凭据只以 `CredentialRef` 引用跨边界传输，明文不进入协议帧、命令行、计划或日志。

ROADMAP §2 的非目标明确写着「不托管用户代码与密钥（构建可本地或自建农场，密钥只以引用形式出现）」。托管服务会直接改变这条边界：项目从软件提供方变成计算与数据托管方，需要承担租户隔离、密钥托管、数据驻留、审计、滥用处理与 SLA。INITIATIVES M9-D2 要求先做决策，不承诺实现。

## 决策（Decision）

**GA 与 1.x 阶段只支持自托管农场。** 项目不运营农场控制面，不接收、存储或处理用户源码、产物、构建日志或签名密钥；文档、协议与部署指南继续作为交付物。

### 1. 三种形态的结论

| 形态 | 信任边界 | 成本与运维 | 结论 |
|---|---|---|---|
| 仅自托管（当前） | 用户在自有或自租机器上运行 origin 与 worker；项目只发软件 | 用户承担机器、工具链、网络与密钥；项目承担协议、文档与缺陷修复 | **GA 采用**；补齐生产部署清单与演练 |
| 多租户托管 | 项目运营控制面与 runner，接收用户源码 / 产物，可能托管密钥引用或明文 | 控制面、隔离、配额、密钥托管、审计、驻留、SLA、计费、滥用处理、on-call | **GA 不做**；需另立项目与后继 ADR |
| BYOC（用户自带云） | 用户云账号内跑 runner；项目只提供部署模板与镜像，不接触数据面 | 比多租户低，但仍需维护部署模板、版本兼容与支持矩阵 | **若未来做托管，优先于多租户**；本 ADR 不实现 |
| 合作伙伴托管 | 第三方运营，项目背书 | 治理、责任边界与品牌风险由项目承担 | **不做**；无法控制隔离与合规 |

### 2. 信任边界（仅自托管）

| 数据 / 能力 | 所在位置 | PolyPack 项目可见性 | 责任方 |
|---|---|---|---|
| 用户源码 | 发起地 + 用户构建地 | 不可见；项目不运营中转 | 用户 |
| 明文签名密钥 / 口令 | 构建地本机 keyring / Vault / env | 不可见；只以 `CredentialRef` 引用出现 | 用户 |
| 产物与摘要 | 构建地产出，经用户选择的传输回发起地 | 不可见 | 用户 |
| 构建日志 / 诊断 | 发起地与构建地本地 | 默认不可见；仅用户主动提交 issue 时 | 用户 |
| 共享缓存 / 对象存储 | 用户自有目录或用户云账号 | 不可见 | 用户 |
| 农场协议实现与文档 | 仓库与发行包 | 公开 | 项目 |

协议边界保持不变：`JobSpec.secrets` 只装引用；worker 在执行时向本机后端取值；仓库出现明文凭据即构建失败（`polypack scan`）。项目不提供「托管密钥」后门，因为这与 ROADMAP §7 的「密钥零入库、凭据只以引用出现」冲突。

### 3. 为什么 GA 不做托管

- **原则冲突**：托管会自动获得用户代码与构建环境，即使不存密钥，也已经成为用户代码的处理者；必须显式改写 ROADMAP §2，不能靠解释绕过。
- **隔离成本**：真正的多租户需要每租户独立 VM / runner（仅进程隔离不足以承载不可信构建），加网络出站策略、缓存命名空间隔离、产物加密与清理证明；macOS 宿主还受 Apple 虚拟化与许可约束，容量与成本显著高于 Linux。
- **密钥托管**：托管签名意味着项目持有或代理解锁用户密钥；需要 KMS / HSM、租户级授权、审计与轮换。若坚持「项目永不接触明文」，托管服务的能力会被削到接近 BYOC，商业价值有限。
- **合规与责任**：数据驻留、DPA、子处理方清单、事件响应、SOC 2 / ISO 27001 类证明、滥用处理与执法请求流程，都是独立于代码的长期义务。
- **运维规模**：控制面、队列、自动扩缩、配额、计费、7×24 on-call 与 SLA 需要专职团队；当前项目没有对应的运营承诺。
- **信任叙事**：PolyPack 的卖点是本地 / 自建与可验证产物；托管会稀释「不托管用户代码与密钥」这一差异点。

### 4. 若未来提供托管，ROADMAP 原则必须如何修改

任何托管形态都必须先由**后继 ADR** 取代本 ADR，并完成下表的原则改写；不得在文档中静默重新解释「不托管」。

| 现状 | 托管所需修改 | 退出证据 |
|---|---|---|
| ROADMAP §2「不托管用户代码与密钥」 | 改为「默认不托管；托管为显式选择加入的独立服务」，列明托管的数据类别与不托管的数据类别 | 修订后的原则经维护者评审并双语同步 |
| 密钥只以引用出现 | 定义托管密钥的边界：BYOK / 用户 KMS / 项目 KMS 三选一；若项目持有明文，必须写入风险接受与审计方案 | 密钥托管威胁模型与渗透测试 |
| 构建可本地或自建农场 | 增加「项目托管构建」作为第三种部署形态，并声明默认关闭 | FARM / FARM-DEPLOY / README 同步 |
| 诚实分级 | 托管能力单独分级，不得把托管 runner 写成「已验证」除非有真实环境证据 | ENV-SLOTS 与发布说明 |
| 不做应用商店本身 | 不变；托管只做构建，不做分发市场 | 范围声明 |

同时必须补齐：租户隔离与逃逸测试、数据分类与保留期、数据驻留与子处理方清单、事件响应与泄露通知、SLA 与信用条款、滥用与加密挖矿 / 凭据窃取处理、计费与配额、支持渠道、保险与责任限制。缺少任何一项都不应上线。

### 5. 成本与运维模型（托管）

| 成本项 | 内容 | 自托管对应项 |
|---|---|---|
| 计算 | 每租户隔离 runner；macOS 容量与许可溢价最高 | 用户自购 / 自租 |
| 控制面 | API、调度、队列、配额、计费、审计 | 无（共享目录 / 用户传输） |
| 存储与带宽 | 源码暂存、产物、缓存、日志；加密与生命周期 | 用户自有 |
| 密钥 | KMS / HSM、租户授权、轮换、审计 | 用户本机 keyring / Vault |
| 安全 | 隔离测试、渗透测试、漏洞响应、滥用处理 | 项目只修软件缺陷 |
| 合规 | DPA、驻留、子处理方、审计报告 | 用户自行评估 |
| 运营 | on-call、SLA、状态页、支持与退款 | 社区 / 用户自运维 |

该表是预算科目，不是报价；任何具体定价都需要独立商业评审。

### 6. 重开条件（何时重新考虑）

只有同时满足以下条件，才启动后继 ADR 评估托管：

1. 持续需求：≥ 5 个外部团队在 ≥ 3 个月内明确要求托管，且愿意为隔离与合规付费；
2. 有独立的运营 owner 与预算，能承担 on-call、SLA 与安全响应；
3. 密钥托管方案与「凭据只以引用出现」不冲突，或已获显式风险接受；
4. 租户隔离、数据驻留与滥用处理通过安全评审；
5. 先用 BYOC 验证部署模板与支持成本，再决定是否做多租户。

若只满足「有人问」，结论仍是自托管 + 文档改进；BYOC 是首选项，不直接跳到多租户。

### 7. 规范边界

- 本 ADR 不实现控制面、计费、租户隔离或 BYOC 模板，不修改 `crates/polypack-cli/src/farm.rs`、`docs/FARM.md`、`docs/FARM-DEPLOY.md`。
- 不改变农场协议 v0 / v1 的线格式与凭据模型；不新增密钥托管能力。
- 不承诺托管服务的发布日期、价格或区域。

## 备选方案（Alternatives）

| 方案 | 未采用的原因 |
|---|---|
| 多租户托管（GA 采用） | 与 ROADMAP §2 非目标直接冲突；隔离、密钥托管、合规与 on-call 成本远超当前范围 |
| BYOC（GA 采用） | 仍需部署模板、版本兼容与支持矩阵；在需求未验证前投入过早 |
| 合作伙伴托管 | 项目仍需为隔离与合规背书，却无法控制实现；责任与品牌风险不对等 |
| 只做托管、不做自托管 | 放弃现有协议与用户信任模型；与「本地优先」定位冲突 |
| 维持现状但不写 ADR | 触发条件出现时会被动决策；无法提前暴露原则冲突与成本 |

## 影响（Consequences）

- 没有 macOS 机器的用户仍需自备 / 自租 Mac 或使用现有 CI；这是 GA 的已知限制，应写入文档而不是用托管掩盖。
- 项目不获得托管收入，也不承担用户代码与密钥的处理责任；信任叙事保持简单。
- 自托管部署质量成为关键：生产部署清单、升级兼容、故障排查与缓存后端验证需要继续投入。
- 若需求增长，BYOC 与托管评估有明确门槛；不会因单个请求临时改口。
- 未来若托管，必须走「后继 ADR + ROADMAP 原则修订 + 安全 / 合规评审」三件套，成本高但路径清晰。
